1. Tujuan produk

Inventory PPE adalah aplikasi web internal untuk mengelola stok alat pelindung diri (PPE) per gudang/proyek. Aplikasi dipakai HSE, admin gudang, dan manajer agar:

  • Stok PPE tercatat per gudang, termasuk varian ukuran.
  • Personel yang diberangkatkan (mobilisasi) membawa kelengkapan sesuai posisi kerja.
  • Barang yang kembali (demobilisasi) dicek: layak, rusak, atau hilang.
  • Permintaan pengadaan (Material Request / MR) dan peminjaman antar gudang tercatat.
  • Akses dibatasi berdasarkan peran dan penugasan gudang.
Hasil yang diharapkan dari sistem: stok gudang selalu mencerminkan barang fisik; personel Onsite tidak bisa dimobilisasi ulang sebelum demob selesai; HSE meng-approve item bermasalah dan pemakaian spare; SuperAdmin mengatur akun dan data master.

3. Cara masuk (autentikasi)

3.1 Halaman login — /login

Judul kartu: Masuk ke Inventory PPE. Pendaftaran publik, lupa password, dan verifikasi email tidak tersedia (/register = 404).

  1. Masuk dengan Google (tombol merah, utama): hanya email yang sudah didaftarkan SuperAdmin. Jika domain Workspace dikonfigurasi, hanya email @domain itu. Email belum terdaftar → “Email {email} belum terdaftar…”. Akun nonaktif → “Akun ini dinonaktifkan. Hubungi SuperAdmin.” Setelah sukses, masuk ke Daftar Gudang (/home).
  2. Cadangan SuperAdmin (email & password): form email + password + “Ingat saya” + tombol Login. Akun nonaktif harus logout otomatis dan menampilkan pesan nonaktif.

User yang sudah login membuka / diarahkan ke /home. Tamu diarahkan ke /login. Semua halaman lain butuh sesi login.

4. Pilih gudang lalu masuk aplikasi

Setelah login, user melihat Daftar Gudang. Setiap kartu menampilkan nama gudang, nomor kontrak, ID GDG-xxx.

  • Gudang berhak: badge Aktif, tautan Masuk →. Klik menyimpan gudang di sesi dan membuka Dashboard.
  • Gudang tidak berhak: badge Tidak ada akses, teks Terkunci, klik tidak mengubah sesi.
  • Belum ada data gudang: “Belum ada data gudang.” SuperAdmin mendapat tautan Sync Data Master; peran lain diminta minta SuperAdmin sync.
  • Tombol Keluar mengakhiri sesi.
  • Membuka Dashboard tanpa gudang terpilih → kembali ke Daftar Gudang: “Pilih gudang terlebih dahulu untuk membuka dashboard.”
  • Di dalam modul, tombol Ganti Gudang kembali ke Daftar Gudang.

Semua operasi stok/personel/mob-demob bersifat per gudang yang sedang aktif, kecuali status personel Onsite/Offsite yang disinkronkan lintas gudang berdasarkan identitas personel master.

6. Dashboard

Tujuan: ringkasan gudang aktif dan hal yang perlu ditindak.

Kartu ringkasan: Personel, Total Unit Stok, Stok Perlu Atensi, Mobilisasi Aktif. Di bagian bawah juga ada metrik Demob menunggu, MR belum selesai, dan spare menunggu (jika ditampilkan di UI).

Notifikasi (sekali tampil sampai ditutup)

  • Pengajuan peminjaman baru — gudang ini adalah sumber pinjaman, status pending. Teks: “{gudang} mengajukan {qty} unit {barang}.” Tautan “Periksa pengajuan”.
  • Pengajuan disetujui / ditolak — gudang ini adalah peminjam. Jika ditolak, tampilkan alasan.
  • Menutup notifikasi (tombol Tutup) membuat notifikasi itu tidak muncul lagi untuk user yang sama.

Stok Perlu Perhatian

Hanya item level Kritis (merah, qty < min) atau Menipis (kuning). Kosong: “Tidak ada stok kritis atau menipis.” Tautan “Lihat Stok”.

Belum Dikembalikan

Peminjaman berstatus approved yang melibatkan gudang ini, sampai dikembalikan. Tetap muncul setiap refresh (bukan notifikasi sekali tutup). Kosong: “Tidak ada peminjaman yang belum dikembalikan.”

Uji: tanpa gudang di sesi → redirect home. User tanpa akses gudang sesi → logout konteks gudang + pesan tidak punya akses.

7. Data master (sumber barang, gudang, personel, posisi)

Daftar gudang, personel, posisi, barang+varian, dan perlengkapan per posisi bukan diinput di aplikasi ini. SuperAdmin menarik salinan lewat Sync Data Master dari API master. Setelah sync, aplikasi membaca salinan lokal (tetap jalan tanpa internet). Sync gagal tidak boleh mengosongkan data lama.

Endpoint yang di-sync: Gudang, Personel, Posisi, Barang & Varian, Perlengkapan per Posisi. Bisa sync semua atau satu endpoint. Sukses: “Sync berhasil: …”. Gagal sebagian: “Sebagian data gagal di-sync, data lama tetap dipakai.”

Hanya SuperAdmin yang melihat dan menjalankan menu ini.

8. Stok PPE

8.1 Halaman Stok

Tujuan: daftar item yang gudang miliki, qty, kategori, dan indikator Min-Max.

  • Tambah stok: pilih barang/varian dari master yang belum ada di gudang ini, qty ≥ 1, kategori Consumable atau Non Consumable. Barang yang sudah ada tidak boleh ditambah lewat form ini — pesan: “Barang ini sudah ada di stok. Penambahan qty hanya melalui Material Request (MR) atau tombol Ubah.”
  • Ubah: qty ≥ 1, kategori, dan persen Min (opsional). Sukses: “Stok berhasil diperbarui.”
  • Hapus: “Stok berhasil dihapus.”
  • HSE/Manager: hanya melihat, tanpa tombol ubah.

Aturan Min-Max (indikator warna)

Jumlah personel gudang = N. Persen default 10%. Min = max(1, round(N × persen / 100)). Max ideal = N (1 unit per orang).

LevelSyaratContoh N=100, Min=10
Merah (Kritis)qty < Min0–9
Kuning (Menipis)Min s.d. min(2×Min, N)10–20
Abu-abudi atas kuning sampai N−121–99
Hijau (penuh)qty ≥ N≥ 100

Jika N = 0 atau Min = 0, level abu-abu. Dashboard hanya menampilkan merah dan kuning.

8.2 PPE Masuk

Riwayat barang masuk gudang ini: kedatangan dari Material Request dan transfer masuk. Hanya lihat. Kolom mencakup barang, qty datang, tanggal, nomor terkait.

Pencatatan kedatangan MR menambahkan riwayat masuk. Aplikasi memakai halaman ini sebagai jurnal masuk, bukan form input terpisah.

8.3 PPE Keluar

Riwayat barang keluar gudang ini: dikeluarkan saat pengecekan mobilisasi (personel membawa PPE), pemakaian spare yang disetujui, dan transfer keluar. Hanya lihat. Dipakai juga sebagai sumber Data Pemakaian PPE (non-consumable).

8.4 Transfer Barang

Tujuan: memindahkan stok dari gudang proyek ke satu gudang tujuan yang dikonfigurasi (gudang pusat/tujuan transfer).

  • Hanya dari gudang yang bukan gudang tujuan, ke gudang tujuan itu. Sebaliknya ditolak: “Transfer barang hanya dapat dilakukan dari gudang lain ke {nama}.” / “Transfer barang hanya dapat dilakukan ke gudang {nama}.”
  • Input: tanggal, minimal 1 item, qty ≥ 1 dan tidak melebihi stok asal.
  • Sukses: stok asal berkurang, stok tujuan bertambah (item dibuat di tujuan jika belum ada sesuai logika transfer), tercatat di PPE Keluar asal dan PPE Masuk tujuan. Pesan: “Transfer barang ke {nama} berhasil.”
  • Gudang tujuan yang dibuka di menu Transfer melihat status bahwa mereka adalah tujuan (bukan pengirim).

9. Personel

9.1 Data Personel

Daftar personel yang didaftarkan ke gudang ini, dipilih dari master Personel. Setiap orang punya satu atau lebih posisi.

  • Status: Offsite atau Onsite. Onsite karena mobilisasi di gudang lain ditampilkan “Onsite ({Nama Gudang})”.
  • Status disinkronkan lintas gudang lewat ID personel master: dimobilisasi di mana pun → Onsite di semua gudang; demob dimulai → Offsite di semua gudang.
  • Personel yang sudah terdaftar di gudang ini tidak muncul lagi di opsi tambah.
  • CRUD: tambah (wajib personel + posisi), ubah, hapus — SuperAdmin/AdminPPE. HSE/Manager lihat saja.

9.2 Data Pemakaian PPE

Matriks personel × item Non Consumable. Angka = total unit yang pernah keluar untuk orang itu (bukan jumlah transaksi). Klik baris membuka riwayat per item (lintas gudang). Semua peran boleh melihat.

10. Permintaan PPE (Material Request)

10.1 Buat Tabel Permintaan

Hanya SuperAdmin & AdminPPE. Mengisi nomor MR, tanggal, dan item dari stok gudang lalu unduh PDF template. Tidak menyimpan ke Data Permintaan. Dipakai untuk dokumen cetak/pengajuan di luar sistem.

10.2 Data Permintaan

MR yang tersimpan di gudang.

  1. Buat MR: nomor MR wajib, minimal 1 item dari stok gudang, qty ≥ 1. Tanggal = hari ini. Sukses: “Material Request berhasil dibuat.”
  2. Ubah: nomor MR. “Nomor MR berhasil diperbarui.”
  3. Hapus: “Material Request berhasil dihapus.”
  4. Unduh PDF dokumen MR.
  5. Kedatangan per item: tanggal, qty datang ≥ 1, no PO opsional, catatan opsional. Qty datang tidak boleh melebihi sisa yang belum datang. Pesan jika berlebih: “QTY datang melebihi sisa yang belum datang (X).”

Status item: Belum Datang / Sebagian / Sudah Selesai. Status MR: Belum Selesai (semua belum datang), Sebagian, Sudah Selesai (semua item selesai). Dashboard menghitung MR yang belum “Sudah Selesai”.

HSE/Manager boleh buka daftar, detail, dan PDF; tidak boleh buat/ubah/hapus/catat kedatangan.

11. Mobilisasi (keberangkatan ke lokasi kerja)

Tujuan: merencanakan tim, mengalokasikan PPE, memastikan setiap orang lengkap, lalu menjalankan proyek.

11.1 Daftar & buat

  • Daftar hanya mobilisasi berstatus draft atau berjalan (bukan selesai).
  • Buat: SR opsional, lokasi pekerjaan opsional, minimal 1 personel. Hanya personel Offsite di gudang ini, dan yang tidak punya demob tertunda (belum cek / menunggu approval) di gudang mana pun.
  • Posisi default = posisi Data Personel, bisa diubah per orang pada form.
  • Saat disimpan: status mobilisasi = draft; personel menjadi Onsite di semua gudang; perlengkapan per posisi di-seed dari master “Perlengkapan per Posisi”.

11.2 Perlengkapan

  • Jenis perlengkapan: kebutuhan standar per posisi (bisa tambah/ubah/hapus selama masih draft dan belum dikeluarkan dari stok dengan aturan yang berlaku).
  • Jenis by_request: permintaan tambahan. Penerima wajib. Setelah stok dikeluarkan, item by_request untuk user tidak boleh diubah/hapus.
  • Qty tidak boleh melebihi stok tersedia. Pesan stok kurang menyebut nama barang dan qty tersedia vs dibutuhkan.

11.3 Spare barang

SR spare mengalokasikan stok sebagai cadangan di lapangan: stok gudang langsung berkurang. Pemakaian spare oleh personel masuk antrean approval HSE. Approve → sisa spare berkurang + tercatat PPE Keluar. Tolak → tidak terpakai. Spare bisa dikembalikan ke stok (sisa kembali).

11.4 Pengecekan kelengkapan personel

Untuk setiap item yang diharapkan (alokasi posisi + by request):

  • Aksi Ada / Tidak.
  • Consumable: setiap keberangkatan mengeluarkan stok sesuai kebutuhan.
  • Non-consumable: jika personel sudah punya item itu (riwayat keluar lintas gudang), sistem bisa menandai otomatis “Ada”; kekurangan qty tetap “Tidak” sampai stok dikeluarkan.
  • Stok tidak cukup → error, pengecekan tidak lengkap.

Submit personel hanya jika semua item lengkap. “Belum bisa submit. Masih ada PPE yang jumlahnya kurang dari kebutuhan.” Sukses mengisi waktu submit.

11.5 Jalankan proyek

Hanya dari status draft. Semua personel harus sudah submit pengecekan. Status menjadi berjalan, data tampil di Demobilisasi. Error: “Proyek sudah berjalan atau selesai.” / “Semua personel harus menyelesaikan pengecekan terlebih dahulu.”

Hapus mobilisasi draft mengembalikan personel ke Offsite (jika tidak ada mob aktif lain).

HSE/Manager: lihat daftar/detail/perlengkapan, tidak boleh buat/jalankan/ubah pengecekan.

12. Demobilisasi (kepulangan)

Daftar mobilisasi berjalan dan selesai (riwayat).

  1. Selesaikan personel: demob_status = belum cek, tanggal demob = hari ini, personel Offsite di semua gudang. Orang ini tidak boleh dimobilisasi lagi sampai demob selesai (approve atau cek tanpa masalah). Pesan: “Personel di-demob. Silakan lakukan pengecekan kelengkapan.”
  2. Dokumen Mobilisasi: daftar item status “ada” yang dibawa (lihat).
  3. Cek kelengkapan (hanya status belum cek, CRUD): untuk item non-consumable, isi kondisi:
    • layak
    • tidak_layak (wajib qty bermasalah + catatan sesuai form)
    • hilang
    Tanpa item bermasalah → demob langsung selesai. Ada tidak layak/hilang → menunggu_approval. Setelah dicek, form menjadi baca-saja.
  4. Dokumen Demobilisasi: hasil cek (lihat).

Jika semua personel di mobilisasi berstatus demob selesai, status mobilisasi = selesai dan hilang dari daftar Mobilisasi aktif.

13. Approval Demob

Hanya SuperAdmin dan HSE Officer. AdminPPE dan Manager tidak melihat menu dan tidak boleh akses URL.

13.1 Personel menunggu approval

Daftar personel demob_status menunggu_approval. Tampil item bermasalah (tidak layak / hilang) beserta qty dan catatan.

  • Approve: demob selesai, catat waktu approve + catatan opsional. “Approval disetujui. Demob personel selesai.” Jika semua orang di mob itu selesai, mob menjadi selesai.
  • Reject: kembali ke belum cek, hasil cek dihapus agar dicek ulang. “Approval ditolak. Personel dikembalikan ke tahap pengecekan.”

13.2 Pemakaian spare menunggu

  • Approve spare: sisa spare berkurang, tercatat PPE Keluar. “Pemakaian spare disetujui. Sisa spare berkurang dan tercatat di PPE Keluar.”
  • Reject spare: “Pemakaian spare ditolak.” Spare tidak berkurang.

14. Peminjaman PPE antar gudang

Tujuan: gudang A meminjam item yang sudah terdaftar di stok A dari gudang B.

  1. Ajukan (SuperAdmin & HSE): pilih item dari stok gudang peminjam, qty ≥ 1, gudang sumber ≠ gudang sendiri, catatan opsional. Barang harus sudah ada di stok peminjam. Status = pending / UI “Menunggu Approval”. Notifikasi muncul di dashboard gudang sumber.
  2. Approve hanya oleh gudang sumber (user dengan CRUD peminjaman di gudang sumber): stok sumber berkurang, stok peminjam bertambah. Stok sumber harus cukup. Status = approved. Notifikasi ke peminjam. Dashboard “Belum Dikembalikan” aktif di kedua sisi.
  3. Tolak: wajib catatan tolak. Status = rejected / UI “Not Approve”. Stok tidak berubah.
  4. Kembalikan oleh gudang sumber saat status approved: stok peminjam berkurang, stok sumber bertambah. Status = returned. Gagal jika stok peminjam tidak cukup.

AdminPPE dan Manager hanya melihat daftar, tanpa ajukan/approve/tolak/kembalikan.

Daftar menampilkan peminjaman di mana gudang aktif adalah peminjam atau sumber. Kolom: Nama Barang, Qty, Tanggal (pengajuan / diterima / ditolak / barang dikembalikan), Dari, Untuk, Status, Aksi sesuai peran dan sisi gudang.

15. Kelola Akun & Role

Hanya SuperAdmin.

  • Tambah: nama, email unik, peran, aktif/nonaktif, seluruh gudang atau minimal satu gudang. SuperAdmin selalu seluruh gudang. Password acak; user login Google. “Akun berhasil ditambahkan…”
  • Ubah: SuperAdmin tidak boleh menurunkan peran atau menonaktifkan akunnya sendiri.
  • Hapus: tidak boleh hapus diri sendiri.
  • Akun nonaktif tidak bisa login (Google maupun password).

16. Alur ujung-ke-ujung yang wajib lolos uji

  1. Login → pilih gudang → dashboard. Tamu tidak masuk modul. Ganti gudang bekerja. Logout bersih.
  2. Stok awal → MR → kedatangan → PPE Masuk & qty stok naik sesuai kebijakan produk. Status MR berubah Belum Selesai → Sebagian → Sudah Selesai.
  3. Daftar personel Offsite → buat mobilisasi → perlengkapan/pengecekan lengkap → jalankan → muncul di Demobilisasi. Personel Onsite di semua gudang. Tidak bisa dimob lagi.
  4. Demob: selesaikan → cek semua layak → selesai tanpa approval. Bisa dimobilisasi lagi.
  5. Demob: cek ada hilang/rusak → masuk Approval Demob → HSE approve/reject. Reject mengulang cek. Approve menyelesaikan demob.
  6. Peminjaman: HSE gudang A ajukan ke B → notifikasi B → HSE B approve → stok pindah → kembalikan → stok kembali. Tolak tidak mengubah stok. Manager tidak bisa approve.
  7. Transfer hanya ke gudang tujuan yang dikonfigurasi. Stok dan jurnal masuk/keluar konsisten.
  8. RBAC: Manager tidak POST stok/MR/mob. AdminPPE tidak buka Approval Demob, Users, Master Sync. HSE tidak buka Users/Sync/Buat Tabel Permintaan.
  9. IDOR gudang: user gudang 1 tidak bisa CRUD gudang 2 lewat ganti URL.
  10. CSRF: POST tanpa token ditolak (419). Register tetap mati.

18. Yang bukan lingkup produk ini

  • Pendaftaran mandiri, reset password, login SSO selain Google Workspace.
  • Mengelola master gudang/barang/personel/posisi (hanya sync).
  • Aplikasi mobile native, API publik untuk pihak ketiga, pembayaran.
  • Multi-bahasa UI (hanya Indonesia).

19. Persyaratan non-fungsional untuk tes

  • Aplikasi web desktop (sidebar); harus tetap bisa login dan pilih gudang di viewport sempit.
  • Semua POST/PUT/DELETE butuh CSRF dan user terautentikasi.
  • User nonaktif langsung ditendang dari sesi.
  • Halaman modul menampilkan nama gudang aktif agar tester memastikan konteks benar.
  • Setelah aksi sukses/gagal, muncul alert hijau/merah yang bisa ditutup, dan data di tabel sesuai.
Cara memakai dokumen ini saat testing: setiap kasus uji harus merujuk nomor bagian (mis. 11.5 Jalankan proyek). Lulus = UI, pesan, perubahan stok/status, dan hak peran sesuai spesifikasi. Jika kode berbeda dari dokumen ini, itu cacat produk atau cacat dokumen — jangan menyesuaikan tes ke perilaku tak terdokumentasi tanpa keputusan pemilik produk.
